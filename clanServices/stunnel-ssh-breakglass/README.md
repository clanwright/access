# `@clanwright/stunnel-ssh-breakglass`

Provides the `breakglass` role: an isolated, certificate-free TLS 1.3 PSK
listener in front of a separate loopback-only OpenSSH daemon. It is an
emergency path, not a replacement for ordinary administrative access.

```text
Internet -- consumer firewall --> stunnel TLS 1.3 PSK --> 127.0.0.1:sshPort --> recovery sshd
                                                    \--> recovery user --> NOPASSWD sudo
```

The role uses the Access root-pinned `stunnel` and `openssh` packages. It does
not enable or alter the consumer's normal `services.openssh` daemon or
Tailscale service, and it does not open any firewall port. The consumer must
allow only `tlsPort` through its chosen firewall policy.

The role has fixed unit and state names, so place at most one `breakglass`
instance on a machine. Its listener API is IPv4-only and uses unprivileged
ports by design; use a consumer firewall or edge policy for public reachability
rather than granting the service a privileged bind capability.

## Settings and defaults

| Setting                    | Default                        | Constraint                                              |
| -------------------------- | ------------------------------ | ------------------------------------------------------- |
| `tlsPort`                  | `47291`                        | Unprivileged TCP port for the public TLS listener       |
| `sshPort`                  | `47292`                        | Distinct unprivileged TCP port for the loopback backend |
| `listenAddress`            | `0.0.0.0`                      | Valid IPv4 address for stunnel only                     |
| `recoveryUser`             | `access-recovery`              | Safe non-root Unix account name                         |
| `pskSecretName`            | `stunnel-ssh-psk`              | Safe SOPS secret name                                   |
| `authorizedKeysSecretName` | `recovery-ssh-authorized-keys` | Distinct safe SOPS secret name                          |

Ports must differ, the two secret names must differ, and `recoveryUser` cannot
be `root`. The restricted option types prevent values from injecting stunnel,
OpenSSH, shell, or SOPS configuration syntax.

## Credentials and host identity

The role declares exactly two runtime SOPS secrets. Both source files are
`root:root` mode `0400`.

- The PSK source is loaded by systemd as a `LoadCredential` named `psk` for the
  unprivileged stunnel process. It is never put in the Nix store or written to
  the generated stunnel configuration.
- The authorized-public-keys source is loaded as a credential for the recovery
  sshd. At daemon start, a root process stages a runtime-only `root:recovery`
  mode `0440` copy in a `root:recovery` mode `0750` runtime directory. The sshd
  keeps its root UID while systemd assigns its primary group to the configured
  recovery account. OpenSSH reads authorized keys after switching to the target
  account, so both group-readable paths are necessary; the original SOPS source
  stays root-only.

The PSK file is a content contract owned by the consumer: one identity record
whose key is exactly 64 lowercase hexadecimal characters representing 32
random bytes. Do not use arbitrary ASCII passphrases or all-hex text of another
length: stunnel treats hexadecimal key material differently from ASCII. The
authorized-key file contains only the intended public SSH keys. Neither file
belongs in this repository, a Nix literal, a client profile, test fixture, or
log.

An independent Ed25519 host key is generated by the host-key service at
consumer boot in the role's persistent state directory. It deliberately does
not reuse the normal sshd host key or depend on `services.openssh.enable`.
Record and distribute its fingerprint through the consumer's recovery process
after boot; Access neither generates a recovery kit nor stores its output.

Secret rotation restarts the affected service: PSK rotation restarts stunnel,
and authorized-key rotation restarts the recovery sshd. A missing or invalid
runtime secret leaves the listener unavailable rather than falling back to a
weaker transport.

## Access boundary

stunnel accepts only TLS 1.3 PSK connections and proxies them to
`127.0.0.1:sshPort`. It disables session resumption and bounds its cache,
timeouts, restart rate, memory, task count, and file descriptors. The stunnel
unit runs with `DynamicUser`, `NoNewPrivileges`, systemd credentials, and a
restricted filesystem/process surface. The native NixOS stunnel service is not
used because its server mode requires a certificate, while this role is
PSK-only.

The inner OpenSSH daemon accepts only the dedicated recovery user. It permits
terminal sessions and the regular SFTP subsystem, but requires public-key
authentication and disables password, keyboard-interactive, host-based, and
GSSAPI authentication. `DisableForwarding` is set along with explicit X11,
agent, TCP, StreamLocal, gateway, and tunnel restrictions. Its listener is
hard-coded to IPv4 loopback, so `sshPort` is never exposed by this role.

The recovery account intentionally has passwordless sudo for a true
break-glass path. Consequently, it is effectively a root-equivalent identity:
limit the PSK and authorized keys to the recovery custodians, preserve the
host-key fingerprint out of band, and remove access by rotating both runtime
materials. The recovery sshd cannot use `NoNewPrivileges` or a read-only
system filesystem because those would prevent the approved sudo recovery work.

The TLS PSK and SSH key are two independent possession checks, but this is not
an MFA claim: a single recovery kit or operator may hold both materials. Use
separate custodians and consumer-owned recovery procedures if independent
approval is required.

Because every decrypted connection reaches sshd from loopback, the daemon sets
`PerSourcePenalties no`; otherwise a failed external client could penalize the
shared `127.0.0.1` source and self-deny all recovery access. `LogLevel VERBOSE`
and `-e` send successful SSH login records to the journal. Consumer-owned
notification routing may act on those records; this role does not block login
on notification delivery.

`KillMode=process` and `stopIfChanged=false` avoid needlessly killing existing
recovery child sessions during ordinary configuration replacement. They do not
guarantee continuity across an emergency-service restart, secret rotation, or
network failure. Before changing the recovery stack from a break-glass shell,
start any critical repair in a detached root-owned process and retain another
recovery route.

## Client and consumer prerequisites

Keep a client configuration only in the consumer-owned recovery kit. This
secret-free template shows the required shape; angle-bracket tokens are
operator-supplied metadata or runtime paths, not values to commit:

```ini
foreground = yes
client = yes

[recovery]
accept = 127.0.0.1:<LOCAL_FORWARD_PORT>
connect = <PUBLIC_IPV4>:<TLS_PORT>
PSKidentity = <PSK_IDENTITY>
PSKsecrets = <LOCAL_RUNTIME_PSK_FILE>
sslVersionMin = TLSv1.3
sslVersionMax = TLSv1.3
```

Then point SSH or SFTP at the local forwarded endpoint. The SSH host entry
must pin the independently generated emergency host key rather than accepting
the normal sshd key:

```sshconfig
Host access-recovery-<SERVER>
  HostName 127.0.0.1
  Port <LOCAL_FORWARD_PORT>
  User access-recovery
  HostKeyAlias <SERVER>-stunnel-ssh-breakglass
  StrictHostKeyChecking yes
  UserKnownHostsFile <CONSUMER_RECOVERY_KIT_KNOWN_HOSTS>
  IdentitiesOnly yes
  IdentityFile <CONSUMER_RECOVERY_PRIVATE_KEY>
```

Direct SSH to the public address and `sshPort` is intentionally unavailable.

Before treating a consumer deployment as usable, its owner should verify the
public firewall exposes only `tlsPort`, the expected TLS 1.3 PSK reaches SSH,
an incorrect or removed PSK fails, direct public SSH fails, SFTP and a terminal
work, forwarding is rejected, and the generated emergency host-key fingerprint
matches the out-of-band record. These are consumer runtime checks, not actions
performed by Access.

## Verification

Run:

```sh
nix build .#checks.x86_64-linux.stunnel-ssh-breakglass-contract
```

The contract evaluates the native Clan manifest and a native NixOS system. It
checks API defaults and input validation, secret metadata and restart wiring,
root-pinned package paths, service ordering/hardening, recovery-user sudo/PAM
wiring, loopback-only OpenSSH policy, and parses the generated sshd
configuration with `sshd -G -T`. It deliberately uses no secret or key fixture;
stunnel parsing and end-to-end TLS authentication remain consumer-runtime
coverage.
